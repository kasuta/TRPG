## 要望の原文（要約）

### A. マイキャラクターの並べ替え
- 「あなたのキャラクター」欄は、現状は登録順（実際はサーバー側で `created_at DESC`＝新しい順）で並んでいる。
- これをドラッグで好きな順番に並べ替えたい。

### B. マイキャラクターのフォルダ
- 自分のPCと、GM用のボスなどを振り分けて置けるようにしたい。
- フォルダは自分で命名できる。階層は1階層まで。
- 「あなたのキャラクター」欄にフォルダとして表示され、クリックすると中身が見えて、そこから選択できるのが理想。
- 「フォルダ作成」ボタンを追加し、Aと同じドラッグ＆ドロップでキャラをフォルダに入れる。

### C. 判定ツール（`sinobigami_tool/`）の改装
- マイキャラクターと紐付ける。機能は総入れ替え。
- **C-1 判定値診断モード**: 現在の判定値（目標値＝5＋距離）の計算を使い、特技表の各マスを判定値で色分けする。5は薄く、6・7・8…と大きいほど濃くして、どこの判定が厳しいか一目で分かるようにする。
- **C-2 セッション用モード**: ボタンで「名前・キャラクター・指定特技」を登録し、そのボタンを押すと、何の特技で判定できるか（判定値）を一発で表示する。
  - シノビガミでは特技が列（分野）単位で使えなくなることがあるので、列ごとに「消える」ボタンを付け、押している間はその列の特技を使えないものとして自動計算する。
  - 登録したボタンは、キャラクター名が違えば別の色で表示する（どのキャラがその攻撃を打ったかを一目で判別するため）。

## 現状の確認（コード調査の結果）

- 一覧の取得: `GET /api/my-characters` は `ORDER BY created_at DESC`。並び順・フォルダを保存する列やテーブルは無い（`characters` は `id, data, image_url, created_at, user_id, updated_at, game`）。
- 一覧の描画: `sinobigami/index.js` の `renderListItems` / `renderMyCharacters` / `applyGameFilter`（マギロギ側も同じ構造の別コピー）。ゲーム種別のフィルタタブ（すべて/シノビガミ/マギロギ）がある。
- 判定ツール: `sinobigami_tool/index.html` の単一ファイル。現状はJSONファイルを読み込み、特技表のマスをクリックすると各キャラの習得特技ごとの目標値（5＋距離、ギャップの塗りつぶしを考慮）を表示する。バックエンドとの通信は無い。
  - 読み込むJSONは旧形式（`data.inputs` / `data.checkboxes`）。サーバーの保存形式（`compactifyForShare` の短縮形）とは異なる。
- ログイン情報: トークンは `localStorage` の `sinobigami_auth_token`（両アプリ共通）。ツールも同じオリジン（`kasuta/TRPG`）なので、同じトークンを読める。

## 機能A 実装計画（2026-09-26 承認）

### 設計
- **並び順はユーザーごとに1件のJSON（レイアウト）として保存する**。新テーブル `character_layouts(user_id PK, layout TEXT, updated_at)` を追加する。
  - フォルダ（B）も同じJSONに入る形で、今回まとめて定義する。Bではマイグレーションもデプロイも不要になる（Q15）。
  - レイアウトに無いキャラは「一番上・新しい順」に置く。そのため、新規キャラが一番上に来る仕様（Q3）は、保存処理を変えなくても成り立つ。削除済みのIDは、読み出し時に捨てる。
- **並び順の組み立て（マージ）はサーバーで行う**。フロントには自動テストが無いので、ロジックはテストのあるAPI側に置く。
- 既存の `GET /api/my-characters` は変更しない（キャッシュされた古いフロントも動く）。
- API:
  - `GET /api/my-layout`（要ログイン）: 並び順を適用したツリー `{ v: 1, items: [ {type:"character", id, name, game, updatedAt, createdAt}, {type:"folder", id, name, items:[キャラ要約...]} ] }` を返す。
  - `PUT /api/my-layout`（要ログイン）: IDだけのレイアウト `{ v: 1, items: [ {type:"character", id}, {type:"folder", id, name, items:["キャラID", ...]} ] }` を保存する。
  - 検証（400）: 形の不正、IDの形式、キャラIDの重複、フォルダの入れ子、フォルダ名（1〜30文字）、フォルダは100個まで。本文は64KBまで（413）。他人のキャラIDは、エラーにせず取り除く。
- ローカル確認: APIは `wrangler dev`（8787）で起動し、`.dev.vars` の `EXTRA_ALLOWED_ORIGINS` でだけ localhost を許可する。フロントは localhost で開いたときだけ、ローカルAPIに接続する。

### 機能要件
1. ログイン中の「あなたのキャラクター」一覧で、キャラの行をドラッグして上下に並べ替えられる。挿入位置は線で示す。
2. 並び順はサーバーに保存し、リロードしても、別の端末・ブラウザでも同じ順で表示される。
3. 並び順は、シノビガミとマギロギで共通の1つ。
4. 絞り込みタブを選んだ状態でも並べ替えられる。隠れている他ゲームのキャラの位置は変わらない。
5. 新しく保存したキャラは、一覧の一番上に入る。
6. キャラを削除しても、残りの順番は変わらない。
7. 行のクリックでキャラを開く動作と、削除ボタンは今までどおり動く。
8. 並び順の保存に失敗したら、元の順に戻して失敗を知らせる。

### 非機能要件
- 互換性: `GET /api/my-characters` と、既存のキャラデータ・保存処理は変更しない。デプロイの順は API → フロント。
- 性能: 一覧の取得は1回の通信。並べ替え1回につき保存の通信が1回。保存は順番に送る。
- 上限: 本文は64KBまで、フォルダは100個まで、フォルダ名は30文字まで。
- セキュリティ: ログインが必要。他人のキャラIDは保存時に取り除き、他人のキャラの情報は返さない。
- 障害時: レイアウトが壊れていても、一覧は新しい順で表示される。
- 費用: 今あるD1のテーブルを1つ増やすだけ。
- テスト: APIは vitest。フロントは手動で確認する。
- 同時編集: 後から保存した方が勝つ（競合は検知しない）。
- 保守: 両アプリの `index.js` に同じ処理を、既存の書き方に合わせて入れる。

## 機能B 実装計画（2026-09-26 承認）

### 設計
- **APIの変更は無い**。フォルダの形（`{type:"folder", id, name, items:["キャラID",...]}`、1階層、100個まで、名前1〜30文字）は、Aで `/api/my-layout` に定義済み。反映はフロントの push だけ。
- 名前は、一覧の中の入力欄で直接入力する（ダイアログは使わない。2026-09-26 に決定）。
- 描画: ログイン中の一覧は `renderMyLayoutList()` でツリーを描く。キャラ行のHTMLは `buildListItemHTML(h)` に切り出して、ゲスト履歴と共用する。
- 開閉状態: `localStorage` の `characterListOpenFolders`（開いているフォルダIDの配列。両アプリで共通）。
- 移動: Aの `moveMyCharacter`（スロット方式）を、一般化した `moveLayoutItem` に置き換える。ツリーから取り除いて、対象の前後またはフォルダの中に差し込むので、ほかの項目の相対順は保たれる。
- ドロップ位置:
  | 落とした場所 | 置き場所 |
  |---|---|
  | フォルダ行（閉）: 上25% / 中央50% / 下25% | 前 / 中（末尾） / 後 |
  | フォルダ行（開）: 上25% / 残り | 前 / 中（先頭） |
  | フォルダの中の行 | その行の前後 |
  | ルートの行 | その行の前後 |
  | 一覧の下の余白 | ルートの末尾 |

  フォルダはフォルダの中に入れられない。

### 機能要件
1. 見出しの横に「フォルダ作成」ボタン（ログイン中だけ）。押すと、一番上に入力欄付きの新しいフォルダが出る。Enterで確定、Escで取り消し、空のまま離れても取り消し。
2. フォルダ行: 開閉の印・アイコン・名前・キャラの数・名前変更ボタン・削除ボタン。

## 機能B 改善: ドラッグの当たり判定を「動かしている行の重なり」にする（2026-09-26）

### 経緯
本番で使ってみると、フォルダへの出し入れが直感的ではなかった。判定がマウスの位置だけで決まるため、動かしている行がフォルダに被っていても、マウスがフォルダ行の外にあると中へ入らない。

### 方針（ユーザーが承認）
- ドラッグを始めたときに、掴んだ位置（行の上端からの距離）と行の高さを記録する。ドラッグ中はマウスの位置から、動かしている行の上端と下端を計算する。
- キャラを動かしているとき、動かしている行がフォルダ行の高さの**半分以上**被ったら、そのフォルダの中へ入れる（閉じていれば末尾、開いていれば先頭）。複数に被ったら、重なりの大きい方にする。
- 被りが半分未満なら、動かしている行の**中心**で、ほかの行の前後を決める（今までのマウス位置の代わり）。一覧の下の余白ならルートの末尾、開いた空のフォルダの余白ならその中へ入れる。
- フォルダを動かすときは、中へは入らない（前後だけ）。境目の「半分」は定数 `FOLDER_DROP_OVERLAP` にして、感触に合わせて調整できるようにする。
- 限界:
  - 判定できるのは、マウスが一覧の中にあるときだけ（ドラッグ中のイベントは、マウスの下の要素に届くため）。
  - 半透明の行の描き方はブラウザが決めるので、見た目と判定が数ピクセルずれることがある。

### タスク（1タスク＝1コミット、T4は運用作業）

- [x] T3 `CLAUDE.md` の説明と、この計画書を更新する ← T2

### 結果（ローカルでの確認）
両アプリで、合成したドラッグイベントを使って確かめた。行を中央で掴み、動かしている行の上端の位置を指定した。

- 2つのフォルダに被ったら、重なりの大きい方へ入る。
