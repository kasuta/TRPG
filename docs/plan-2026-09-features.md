## 要望の原文（要約）

### A. マイキャラクターの並べ替え
- 「あなたのキャラクター」欄は、現状は登録順（実際はサーバー側で `created_at DESC`＝新しい順）で並んでいる。
- これをドラッグで好きな順番に並べ替えたい。

### B. マイキャラクターのフォルダ
- 自分のPCと、GM用のボスなどを振り分けて置けるようにしたい。
- フォルダは自分で命名できる。階層は1階層まで。
- 「あなたのキャラクター」欄にフォルダとして表示され、クリックすると中身が見えて、そこから選択できるのが理想。
- 「フォルダ作成」ボタンを追加し、Aと同じドラッグ＆ドロップでキャラをフォルダに入れる。

### C. 判定ツール（`sinobigami_tool/`）の改装
- マイキャラクターと紐付ける。機能は総入れ替え。
- **C-1 判定値診断モード**: 現在の判定値（目標値＝5＋距離）の計算を使い、特技表の各マスを判定値で色分けする。5は薄く、6・7・8…と大きいほど濃くして、どこの判定が厳しいか一目で分かるようにする。
- **C-2 セッション用モード**: ボタンで「名前・キャラクター・指定特技」を登録し、そのボタンを押すと、何の特技で判定できるか（判定値）を一発で表示する。
  - シノビガミでは特技が列（分野）単位で使えなくなることがあるので、列ごとに「消える」ボタンを付け、押している間はその列の特技を使えないものとして自動計算する。
  - 登録したボタンは、キャラクター名が違えば別の色で表示する（どのキャラがその攻撃を打ったかを一目で判別するため）。

## 現状の確認（コード調査の結果）

- 一覧の取得: `GET /api/my-characters` は `ORDER BY created_at DESC`。並び順・フォルダを保存する列やテーブルは無い（`characters` は `id, data, image_url, created_at, user_id, updated_at, game`）。
- 一覧の描画: `sinobigami/index.js` の `renderListItems` / `renderMyCharacters` / `applyGameFilter`（マギロギ側も同じ構造の別コピー）。ゲーム種別のフィルタタブ（すべて/シノビガミ/マギロギ）がある。
- 判定ツール: `sinobigami_tool/index.html` の単一ファイル。現状はJSONファイルを読み込み、特技表のマスをクリックすると各キャラの習得特技ごとの目標値（5＋距離、ギャップの塗りつぶしを考慮）を表示する。バックエンドとの通信は無い。
  - 読み込むJSONは旧形式（`data.inputs` / `data.checkboxes`）。サーバーの保存形式（`compactifyForShare` の短縮形）とは異なる。
- ログイン情報: トークンは `localStorage` の `sinobigami_auth_token`（両アプリ共通）。ツールも同じオリジン（`kasuta/TRPG`）なので、同じトークンを読める。

## 機能A 実装計画（2026-09-26 承認）

### 設計
- **並び順はユーザーごとに1件のJSON（レイアウト）として保存する**。新テーブル `character_layouts(user_id PK, layout TEXT, updated_at)` を追加する。
  - フォルダ（B）も同じJSONに入る形で、今回まとめて定義する。Bではマイグレーションもデプロイも不要になる（Q15）。
  - レイアウトに無いキャラは「一番上・新しい順」に置く。そのため、新規キャラが一番上に来る仕様（Q3）は、保存処理を変えなくても成り立つ。削除済みのIDは、読み出し時に捨てる。
- **並び順の組み立て（マージ）はサーバーで行う**。フロントには自動テストが無いので、ロジックはテストのあるAPI側に置く。
- 既存の `GET /api/my-characters` は変更しない（キャッシュされた古いフロントも動く）。
- API:
  - `GET /api/my-layout`（要ログイン）: 並び順を適用したツリー `{ v: 1, items: [ {type:"character", id, name, game, updatedAt, createdAt}, {type:"folder", id, name, items:[キャラ要約...]} ] }` を返す。
  - `PUT /api/my-layout`（要ログイン）: IDだけのレイアウト `{ v: 1, items: [ {type:"character", id}, {type:"folder", id, name, items:["キャラID", ...]} ] }` を保存する。
  - 検証（400）: 形の不正、IDの形式、キャラIDの重複、フォルダの入れ子、フォルダ名（1〜30文字）、フォルダは100個まで。本文は64KBまで（413）。他人のキャラIDは、エラーにせず取り除く。
- ローカル確認: APIは `wrangler dev`（8787）で起動し、`.dev.vars` の `EXTRA_ALLOWED_ORIGINS` でだけ localhost を許可する。フロントは localhost で開いたときだけ、ローカルAPIに接続する。

### 機能要件
1. ログイン中の「あなたのキャラクター」一覧で、キャラの行をドラッグして上下に並べ替えられる。挿入位置は線で示す。
2. 並び順はサーバーに保存し、リロードしても、別の端末・ブラウザでも同じ順で表示される。
3. 並び順は、シノビガミとマギロギで共通の1つ。
4. 絞り込みタブを選んだ状態でも並べ替えられる。隠れている他ゲームのキャラの位置は変わらない。
5. 新しく保存したキャラは、一覧の一番上に入る。
6. キャラを削除しても、残りの順番は変わらない。
7. 行のクリックでキャラを開く動作と、削除ボタンは今までどおり動く。
8. 並び順の保存に失敗したら、元の順に戻して失敗を知らせる。

### 非機能要件
- 互換性: `GET /api/my-characters` と、既存のキャラデータ・保存処理は変更しない。デプロイの順は API → フロント。
- 性能: 一覧の取得は1回の通信。並べ替え1回につき保存の通信が1回。保存は順番に送る。
- 上限: 本文は64KBまで、フォルダは100個まで、フォルダ名は30文字まで。
- セキュリティ: ログインが必要。他人のキャラIDは保存時に取り除き、他人のキャラの情報は返さない。
- 障害時: レイアウトが壊れていても、一覧は新しい順で表示される。
- 費用: 今あるD1のテーブルを1つ増やすだけ。
- テスト: APIは vitest。フロントは手動で確認する。
- 同時編集: 後から保存した方が勝つ（競合は検知しない）。
- 保守: 両アプリの `index.js` に同じ処理を、既存の書き方に合わせて入れる。

## 機能B 実装計画（2026-09-26 承認）

### 設計
- **APIの変更は無い**。フォルダの形（`{type:"folder", id, name, items:["キャラID",...]}`、1階層、100個まで、名前1〜30文字）は、Aで `/api/my-layout` に定義済み。反映はフロントの push だけ。
- 名前は、一覧の中の入力欄で直接入力する（ダイアログは使わない。2026-09-26 に決定）。
- 描画: ログイン中の一覧は `renderMyLayoutList()` でツリーを描く。キャラ行のHTMLは `buildListItemHTML(h)` に切り出して、ゲスト履歴と共用する。
- 開閉状態: `localStorage` の `characterListOpenFolders`（開いているフォルダIDの配列。両アプリで共通）。
- 移動: Aの `moveMyCharacter`（スロット方式）を、一般化した `moveLayoutItem` に置き換える。ツリーから取り除いて、対象の前後またはフォルダの中に差し込むので、ほかの項目の相対順は保たれる。
- ドロップ位置:
  | 落とした場所 | 置き場所 |
  |---|---|
  | フォルダ行（閉）: 上25% / 中央50% / 下25% | 前 / 中（末尾） / 後 |
  | フォルダ行（開）: 上25% / 残り | 前 / 中（先頭） |
  | フォルダの中の行 | その行の前後 |
  | ルートの行 | その行の前後 |
  | 一覧の下の余白 | ルートの末尾 |

  フォルダはフォルダの中に入れられない。

### 機能要件
1. 見出しの横に「フォルダ作成」ボタン（ログイン中だけ）。押すと、一番上に入力欄付きの新しいフォルダが出る。Enterで確定、Escで取り消し、空のまま離れても取り消し。

## 機能B 改善: ドラッグの当たり判定を「動かしている行の重なり」にする（2026-09-26）

### 経緯
本番で使ってみると、フォルダへの出し入れが直感的ではなかった。判定がマウスの位置だけで決まるため、動かしている行がフォルダに被っていても、マウスがフォルダ行の外にあると中へ入らない。

### 方針（ユーザーが承認）
- ドラッグを始めたときに、掴んだ位置（行の上端からの距離）と行の高さを記録する。ドラッグ中はマウスの位置から、動かしている行の上端と下端を計算する。
- キャラを動かしているとき、動かしている行がフォルダ行の高さの**半分以上**被ったら、そのフォルダの中へ入れる（閉じていれば末尾、開いていれば先頭）。複数に被ったら、重なりの大きい方にする。
- 被りが半分未満なら、動かしている行の**中心**で、ほかの行の前後を決める（今までのマウス位置の代わり）。一覧の下の余白ならルートの末尾、開いた空のフォルダの余白ならその中へ入れる。
- フォルダを動かすときは、中へは入らない（前後だけ）。境目の「半分」は定数 `FOLDER_DROP_OVERLAP` にして、感触に合わせて調整できるようにする。
- 限界:
  - 判定できるのは、マウスが一覧の中にあるときだけ（ドラッグ中のイベントは、マウスの下の要素に届くため）。
  - 半透明の行の描き方はブラウザが決めるので、見た目と判定が数ピクセルずれることがある。

### 設計
#### API（`sinobigami-api`。まとめて1回で公開する）
- **レイアウトの形式 v2**:
  - フォルダに `kind`（`"sinobigami"` / `"magirogi"` / `"general"`）を持たせる。
  - 1段目のフォルダの `items` には、キャラID（文字列）とサブフォルダ（`{type:"folder", id, name, kind, items:["キャラID", ...]}`）を混ぜて入れられる。
  - サブフォルダの中は、キャラIDだけにする。
  - `GET /api/my-layout?v=2` の返り値:
    ```
    { v: 2, items: [
      {type:"character", ...要約},
      {type:"folder", id, name, kind, items: [
        {type:"character", ...要約},
        {type:"folder", id, name, kind, items: [要約...]}
      ]}
    ]}
    ```
- **検証（400）**。今の検証に次を足す。
  - 3段目以降のフォルダ
  - `kind` の値が不正なもの
  - サブフォルダの種別が親と合わないもの（親が一般なら、どの種別でもよい）
  - フォルダの種別とキャラのゲームが合わないもの（キャラのゲームは、持ち主の確認と同じ問い合わせで得る）
  - フォルダの合計が100個を超えるもの
- **今あるフォルダの移行**:
  - D1 のマイグレーションはしない。保存済みの v1 は、読み込むときに `kind` の無いフォルダを一般として扱う（＝今あるフォルダは、すべて一般フォルダになる）。
  - 次に保存したときに v2 の形で書かれる。
  - 公開の前には、いつもどおりバックアップを取る。
- **互換性（Q43 で API を先に公開するため、公開中の古いフロントを壊さない）**:
  - `GET /api/my-layout`（`?v=2` なし）は、今までどおり v1 の形を返す。`kind` は付けず、サブフォルダの中のキャラは親フォルダの中へ平らにして返す。
  - `PUT` で v1 を受け取ったときは、次のようにする。
    - 保存済みのレイアウトにサブフォルダが無ければ、今までどおり保存する。`kind` は保存済みの値を引き継ぎ、無ければ一般にする。
    - サブフォルダがあれば 409「ページを再読み込みしてください」を返し、サブフォルダが消えるのを防ぐ。
  - 判定ツールも、D・E の公開のときに `?v=2` へ切り替える。
- **一覧の要約（`toCharacterSummary`）に足すもの**:
  - `furigana`: `i.fu`
  - `tags`: 短縮形の `tg`。文字列だけ、1〜20文字のものを先頭から5個まで取り出す。
  - `kind`: シノビガミだけ。`i.kd`。無ければ `"shinobi"`。
  - `GET /api/my-characters` にも同じ要約が返る（キーが増えるだけなので互換）。
- テストは vitest で書く。対象は、v2 の検証・v1 からの移行・`?v=2` の有無・409・要約。

#### フロント（両アプリ。F はシノビガミだけ）
- **F. 区分**:
  - 入力欄 `char_kind`（セレクト: シノビ / エネミー）を足し、`INPUT_KEY_MAP` に `kd` を足す。値が無ければシノビにする。
  - エネミーのときは、次のように変える。
    - 生命力の見出しを「生命力」にする（キャラシと画像出力）。
    - CCFOLIA のステータスを `[{生命力: life_extra}, {忍具}]` にする（`value` と `max` は今と同じ決め方）。
  - コマンド・パラメータ・`externalUrl` は変えない。
- **D・E. フォルダ**:
  - 描画・移動・保存（`flattenLayoutItems` / `renderMyLayoutList` / `buildFolderHTML` / `moveLayoutItem` / `resolveDrop` / `toLayoutPayload` / `removeFromLayoutItems`）を、2段に広げる。
  - 種別の表示と絞り込み:
    - フォルダの行に種別の印を付ける（シノビガミ用・マギロギ用は、ゲームのバッジと同じ配色）。
    - シノビガミ用・マギロギ用のフォルダは、そのゲームのタブと「すべて」のときだけ表示する。
  - 作成・変更:
    - 作成中と名前の変更中は、入力欄の横に種別のセレクトを出す。
    - 1段目のフォルダの行に「サブフォルダ作成」ボタンを付ける。スマホでも使える。
    - 削除できるのは、キャラもサブフォルダも無いフォルダだけ。
  - ドロップ:
    - キャラは、種別の合うフォルダ・サブフォルダにだけ入る。
    - サブフォルダを持たないフォルダは、種別の合う1段目のフォルダに入る。判定は、キャラと同じく重なりが `FOLDER_DROP_OVERLAP` 以上かどうか。
    - 入らない組み合わせのときは、中へ入れる枠を出さず、前後に置く。
  - `/api/my-layout?v=2` を使い、`PUT` も v2 で送る。
  - 判定ツールは2段のフォルダを読み、マギロギ用のフォルダは出さない。
- **G. タグ**:
  - キャラシの基本情報にタグの入力欄を置く。チップで表示し、入力と Enter で追加、× で外す。
  - 候補は、ログイン中なら一覧の要約のタグから出す。ゲストのときは、候補無しで入力だけできる。
  - `buildSaveData` / `applyLoadedData` / `compactifyForShare` / `expandFromShare` にタグ（`tags` ↔ `tg`）を足す。
  - 一覧の行には、タグを小さく表示する。
- **H. 検索**:
  - ログイン中の一覧の上に、次の3つを置く。
    - 名前の検索欄
    - タグのチップ（使われているタグ）
    - シノビガミの区分の絞り込み（すべて / シノビ / エネミー）
  - 条件は、ゲームのタブとすべて AND で組み合わせる。
  - 名前は NFKC・小文字・カタカナ → ひらがなに揃えて、名前とふりがなの部分一致で探す。
  - 検索中は次のようにする。
    - 一致を含むフォルダだけを残し、自動で開く（開閉の記憶は変えない）。
    - ドラッグと、フォルダの作成・名前の変更をできなくする。
  - 検索条件はブラウザに記憶しない（仮）。

### 機能要件
**D. フォルダの種別**
1. フォルダは、シノビガミ用・マギロギ用・一般のいずれか。作成時に選ぶ（初期値は今のタブ。すべて → 一般）。名前の変更と同じところで、後から変えられる。
2. シノビガミ用はシノビガミのタブと「すべて」、マギロギ用はマギロギのタブと「すべて」、一般はすべてのタブで表示する。一般の中身は、タブで絞る。
3. シノビガミ用・マギロギ用には、そのゲームのキャラだけが入る。一般には両方入る。中身と合わない種別には変えられない。
4. 今あるフォルダは、すべて一般になる。名前・中身・並び順は変わらない。

**E. フォルダの階層**
1. 1段目のフォルダの中に、サブフォルダを作れる（2段まで）。サブフォルダの種別は、親に合わせる（Q25）。
2. PC のドラッグで、キャラをサブフォルダへ入れる・出す・並べ替えることができる。サブフォルダを持たないフォルダは、別の1段目のフォルダへ入れる・出すことができる。
3. フォルダの数は、サブフォルダも含めて合計100個まで。削除できるのは、空のフォルダ（キャラもサブフォルダも無い）だけ。
4. 開閉の記憶・名前の変更・失敗時に元へ戻す動作は、1段目と同じ。スマホでも、表示・開閉・作成・名前の変更・削除ができる。
5. 判定ツールのマイキャラ選択でも、2段のフォルダが表示される（シノビガミ用と一般だけ）。

**F. シノビ/エネミーの区分**（シノビガミ）
1. キャラシに「区分」（シノビ / エネミー）を置く。既定と既存のキャラはシノビ。
2. エネミーのときは、生命力の欄の見出しが「生命力」になる。画像出力の見出しも同じ。値は、追加生命力と同じ欄に入る。
3. エネミーを CCFOLIA 形式でコピーすると、ステータスは「生命力」と「忍具」だけになる。コマンド・パラメータ・名前・共有リンクは、シノビと同じ。
4. 区分は保存・JSON・共有リンクに含まれる。
5. 一覧では、エネミーにバッジを付ける。
6. 区分の選択肢は、後から足せる作りにする。

**G. タグ**
1. 両アプリのキャラシで、タグを5個まで付け外しできる。名前は1〜20文字で、同じキャラに同じタグは付かない。
2. 入力すると、自分のキャラで使っているタグが候補に出る。新しい言葉は、そのまま新しいタグになる。
3. タグは保存・JSON・共有リンクに含まれる。
4. ログイン中の一覧の行に、タグを表示する。

**H. 検索**
1. ログイン中の一覧（両アプリ）で、名前とふりがなの部分一致で検索できる。ひらがなとカタカナ、全角と半角、大文字と小文字は区別しない。
2. タグのチップを選んで絞り込める。複数選ぶと、すべてのタグを持つキャラ（AND）が残る。
3. シノビガミの区分（シノビ / エネミー）でも絞り込める。
4. 条件は、ゲームのタブと組み合わせる。検索中は、一致を含むフォルダだけを自動で開いて表示する。ドラッグとフォルダの編集はできない。
5. 条件を消すと、元の一覧（記憶している開閉の状態）に戻る。

### 非機能要件
- **互換性**:
  - 既存のキャラデータ・共有リンク・JSON は、そのまま読める（区分なし＝シノビ、タグなし）。
  - 古いフロントは、API の公開後もフロントの公開までそのまま動く。
    - `?v=2` の無い `GET` は v1 の形で返る。
    - v1 の `PUT` は、サブフォルダが無ければ通る。
  - `/api/load` と `save` / `update` の形は変えない。
- **データ量**:
  - 保存は今の64KBの上限の中に収まる（タグは最大 5×20 文字）。
  - レイアウトは、フォルダ100個でも64KBに収まる。
- **性能**: 一覧の取得は1回の通信。検索と絞り込みはブラウザの中だけで行い、通信しない。操作1回につき、保存の通信は1回。
- **セキュリティ**:
  - 今と同じく、ログインが必要な API は持ち主だけが使える。
  - タグとフォルダ名は、表示するときに必ずエスケープする。
  - タグは共有リンクで他の人にも見える（Q30。キャラシの注意書きに書く）。
- **公開の手順**: API（バックアップ → デプロイ → スモークテスト）→ フロントを F → D・E → G → H の順。本番に反映する操作は、毎回実行前に確認を取る。
- **テスト**: API は vitest。フロントは、ローカル API とブラウザで手動で確認する（今までどおり）。
- **保守**:
  - 両アプリの `index.js` に、同じ処理を今の書き方で入れる。
  - 区分とフォルダの種別の値は、定数の表で持ち、後から足しやすくする。

## 第3期: キャラ一覧の立ち絵サムネイル（2026-09-29〜。計画は承認済み）

### Context
ログイン中のキャラ一覧に、立ち絵を表示したい。ただし、アクセスが大きく増えるならやめる。

#### 見積もり（2026-09-29 の調査）
- 今の立ち絵: 45枚、27.8MB（中央値 172KB、平均 632KB、最大 3.3MB）。
- 配信（`GET /api/image/:id`）は `max-age=0` で、しかも毎回、画像全体を送り直している（304 を返さない）。
- 元の画像をそのまま一覧に出した場合
  - リクエスト数は無料枠の範囲に収まる。
  - 一覧を開くたびに数MB〜十数MB を読み込み、スマホでは重い。
- そこで、次の方式にする（ユーザーが選択）。
  - 保存時にブラウザで小さなサムネイルを作る。
  - 一覧ではそれを表示し、URL に版を付けて長くキャッシュさせる。
- あわせて、次の2つの無駄も減らす。
  - 保存のたびに元の画像を送り直している。
  - 元の画像に 304 を返していない。

仕様は Q44〜Q50 で決まった。（この節は、`1dab386` の草案を、承認された計画で置き換えたもの）


### 決定事項（一問一答。2026-09-29）
| # | 論点 | 決定 | 補足 |
|---|---|---|---|
| Q44 | サムネイルの形 | **切らずに全体を縮小** | 縦長のまま、長い辺を 128px に縮める（拡大はしない） |
| Q45 | 今ある立ち絵のサムネイル | **一覧を開いたときに自動で作る** | 持ち主がログインして一覧を開くと、サムネイルの無いキャラだけ、ブラウザが元画像を1回読み込んで作り、アップロードする。運用作業は要らない |
| Q46 | 出す場所 | **ログイン中のキャラ一覧だけ** | 両アプリの「あなたのキャラクター」。ゲスト履歴と判定ツールには出さない |
| Q47 | 元の立ち絵の配信 | **ついでに軽くする** | 変更が無ければ 304（中身なし）を返す |
| Q48 | 枠の大きさと、立ち絵の無い行 | **幅36×高さ48px。無い行にも空の枠** | 立ち絵は枠の中に収める（切らない）。無い行には薄い人形のアイコンを出して、名前の位置を揃える |
| Q49 | サムネイルの操作 | **行と同じ（押すとキャラを開く）だけ** | 拡大表示はしない |
| Q50 | 保存のたびの再アップロード | **画像を選び直したときだけ送る** | 普通の保存は、文字のデータだけにする。別のキャラの画像を持ったまま新規保存するとき（共有リンクから開いて保存など）は、今と同じく画像も写す |

### 1. 要件定義（機能要件）
| # | 要件 | 受け入れの条件 |
|---|---|---|
| FR-1 | ログイン中のキャラ一覧（両アプリ）の各行の左に、立ち絵のサムネイルを出す | 幅36×高さ48px の枠に、切らずに収める（縦長・横長とも全体が見える） |
| FR-2 | 立ち絵の無いキャラの行にも、空の枠（薄い人形のアイコン）を出す | 立ち絵の有無にかかわらず、名前の開始位置が揃う |
| FR-3 | 立ち絵を選んで保存すると、サムネイルも作って保存する | 保存後の一覧に、新しいサムネイルが出る。立ち絵を差し替えれば、サムネイルも差し替わる |
| FR-4 | 今ある立ち絵のサムネイルは、持ち主が一覧を開いたときに自動で作る | サムネイルの無いキャラを1体ずつ処理し、できた行から表示が変わる。失敗したキャラがあっても、ほかのキャラの処理は続く |
| FR-5 | サムネイルを押すと、行と同じくキャラを開く | 拡大表示はしない |
| FR-6 | 立ち絵を変えていない保存では、画像を送らない | 上書き保存の通信は、本文の `PUT` だけになる |
| FR-7 | 別のキャラの画像を持ったまま新規保存するときは、今と同じく画像を写す | JSON で画像を読み込んで新規保存したとき、新しいキャラにも立ち絵とサムネイルが付く |
| FR-8 | キャラを削除すると、サムネイルも消える | R2 に `thumb/<id>` が残らない |
| FR-9 | 元の立ち絵に変更が無ければ、送り直さない | 2回目以降の `GET /api/image/:id` は 304（中身なし） |
| FR-10 | 古いフロントで立ち絵を差し替えても、古いサムネイルが残らない | 差し替えでサムネイルが消え、次に新しいフロントで一覧を開いたときに作り直される |

### 2. 非機能要件
| # | 分類 | 要件 |
|---|---|---|
| NFR-1 | データ量 | サムネイルは長い辺 128px の WebP（作れなければ PNG）で、1枚 64KB 以下（見込み 5〜15KB）。一覧の画像は `loading="lazy"` にし、見えている行だけを読み込む |
| NFR-2 | キャッシュ | サムネイルの URL は `…/api/thumb/<id>?v=<版>` とし、`Cache-Control: public, max-age=31536000, immutable` にする。2回目以降の表示や、検索での描き直しでは通信しない |
| NFR-3 | リクエスト数 | 増えるのは、初回の表示と自動作成（1体ずつ・同じページで1回まで）のときだけ。無料枠（Workers は1日10万、R2 の読み出しは月1,000万）に対して問題にならない |
| NFR-4 | 互換性 | 一覧の要約には、キーを足すだけにする（古いフロントも動く）。公開は API → フロントの順。`/api/load` と保存の形は変えない |
| NFR-5 | セキュリティ | サムネイルの保存は、元の画像と同じ権限（持ち主、または持ち主のいないキャラ）にする。形式は先頭のバイトで判定し（png / jpeg / webp）、64KB を超えれば 413。見える範囲は元の画像と同じ |
| NFR-6 | 障害時 | サムネイルの保存に失敗しても、キャラの保存は成功として扱う（自動作成で作り直される）。サムネイルが読めない行は、空の枠を出す |
| NFR-7 | データ | マイグレーションは1回（`0006`、列を1つ足すだけ）。サムネイルは作り直せるので、バックアップの対象にしない |
| NFR-8 | テスト・確認 | API は vitest。フロントは、ローカルの API とブラウザで確かめる（下の「検証」） |
| NFR-9 | 保守 | 両アプリの `index.js` に、同じ処理を今の書き方で入れる。`CLAUDE.md`・AGENTS.md・計画書・開発ログを更新する |
| NFR-10 | 公開 | 本番のバックアップ・マイグレーション・デプロイは、ユーザーが実行する。pages.dev は、ユーザーが手動でデプロイする |
| NFR-11 | 容量（無料枠） | R2 は、今 48 個・32MB。サムネイルで +0.5MB 程度（最悪 +3MB）で、無料枠 10GB の 0.3% のまま。今後も立ち絵1枚あたり +約10KB（元の画像の約1.6%）。D1 は、今 319KB。列の追加で +1KB 未満で、無料枠 5GB に対して無視できる。R2 の書き込み（Class A）は、サムネイルで1回増えるが、保存のたびの元の画像の再アップロードをやめる（FR-6）ので、全体では減る |

### 3. 非要件（スコープ外）
- ゲスト履歴と判定ツールへのサムネイルの表示、マウスを乗せたときの拡大表示
- 元の画像の縮小・変換（上限 5MB はそのまま）、立ち絵の削除ボタン
- サムネイルを一括で作るスクリプト（自動作成で足りる）
- 元の画像の長期キャッシュ（今のまま毎回確認し、304 で軽くするだけ）
- サムネイルの大きさ・切り抜きの選択、既存画像の画質の見直し

### 4. 設計

#### API（`sinobigami-api/src/index.js`）
- **マイグレーション `migrations/0006_thumbnails.sql`**: `ALTER TABLE characters ADD COLUMN thumb_version TEXT;`（NULL はサムネイル無し）
- **R2 のキー**: 同じバケット（`sinobigami_images`）に `thumb/<キャラID>` で置く。
- **一覧の要約**（`toCharacterSummary`）
  - `hasImage: !!row.image_url` と `thumb: row.thumb_version || null` を足す。
  - `/api/my-layout` と `/api/my-characters` の SELECT に、`image_url` と `thumb_version` を足す。
- **`POST /api/upload-thumb/:id`**（`upload-image` の処理を手本にする）
  - `isValidId` で ID を確かめ、キャラが無ければ 404。
  - 権限を確かめる（持ち主がいれば本人だけ。違えば 403）。
  - 元の画像が無ければ（`image_url` が NULL）409。
  - `readBodyLimited(request, MAX_THUMB_BYTES=64KB)` で読む（超えれば 413）。
  - `detectImageType` の結果が png / jpeg / webp のどれかで、宣言した形式と一致しなければ 415。
  - R2 に `thumb/<id>` として置き、`thumb_version = Date.now().toString(36)` にして、`{ version }` を返す。
- **`GET /api/thumb/:id`**
  - R2 の `thumb/<id>` を返す。無ければ 404。
  - ヘッダーは、CORS・`Content-Type`・`ETag`・`Cache-Control: public, max-age=31536000, immutable`・`X-Content-Type-Options: nosniff`。
- **`POST /api/upload-image/:id`**: 元の画像を置いた後に、R2 の `thumb/<id>` を削除し、`image_url` を更新するときに `thumb_version = NULL` も一緒に入れる。
- **`DELETE /api/character/:id`**: 元の画像に加えて、`thumb/<id>` も削除する。
- **`GET /api/image/:id`**
  - `env.sinobigami_images.get(id, { onlyIf: request.headers })` で読む。
  - 本文の無いオブジェクト（条件が一致した）なら、304 と ETag を返す。
  - それ以外は今と同じ。

#### フロント（`sinobigami/index.js` と `magirogi/index.js`。マギロギは字下げが1段深い）
- **定数**: `THUMB_MAX_SIDE = 128`、`THUMB_MAX_BYTES = 64 * 1024`、`THUMB_BOX = 36×48`（CSS）
- **`createThumbnail(blob)`**（グローバル。`escapeHTML` の近く）
  1. `createImageBitmap(blob)` で読む（使えなければ `Image`）。
  2. 倍率 = `min(1, 128 / max(幅, 高さ))` でキャンバスに描く。
  3. `toBlob('image/webp', q)` にする（q は 0.85 → 0.7 → 0.5）。
  4. 返ってきた形式が webp でなければ、`image/png` で作り直す。
  5. 64KB 以下になった Blob を返す。ならなければ null。
- **`uploadThumbnail(id, blob)`**
  - `createThumbnail` の結果を `POST /api/upload-thumb/:id` に送る。
  - 失敗したら `console.warn` だけにし、例外は投げない。
- **画像の出どころ `imageSourceId`**（`savedImageBase64` の隣。DOMContentLoaded の中）
  - `null` にするとき:
    - 画像の入力欄の `change`（sinobigami/index.js:1049 の処理）
    - `applyLoadedData`（JSON からの読み込み）
    - `resetCharacterForm`
  - 共有リンクからの読み込み（index.js:2636）で `compact.img` があるときは、`imageSourceId = match[1]`。
- **`saveCharacter`**（index.js:2552）
  - 画像を送るのは、`imageBase64 && imageSourceId !== id` のときだけにする。
  - 送るときは、元の画像を `upload-image` に送った後、同じ Blob から `uploadThumbnail(id, blob)` を送る。
  - 両方が済んだら、`imageSourceId = id` にする。
- **一覧の行**（`buildListItemHTML`）
  - `h.showThumb` が true のときだけ、`<span class="history-item-thumb">` を名前の左に置く。
    - `h.thumb` があれば `<img src="${API_BASE}/api/thumb/${id}?v=${thumb}" alt="" loading="lazy" width="36" height="48">`。
    - 無ければ、人形の SVG（`LIST_PERSON_ICON`）。
    - `<img>` が読めなければ（`onerror`）、枠だけにする。
  - `renderMyLayoutList` の `charRow` で、`showThumb: true` を渡す。ゲスト履歴は false のまま。
- **自動作成**（`renderMyCharacters` の後）
  - `backfillThumbnails()` を作る。
    - `myCharactersCache` の中の `hasImage && !thumb` のキャラを、1体ずつ `await` で処理する。
      1. `fetch(/api/image/:id)` で元の画像を取得する。
      2. `createThumbnail` でサムネイルを作る。
      3. `upload-thumb` に送る。
      4. 成功したら、`myLayoutItems` の中のその要約の `thumb` を更新して、`renderMyLayoutList()` で描き直す。
  - 同時に1つだけ動かす（`isBackfilling`）。
  - 同じページで失敗したIDは `backfillFailed`（Set）に入れて、もう試さない。
  - `getAuthToken()` が無くなったら止める。
- **CSS**（両アプリの `stylesheet.css`）
  - `.history-item-thumb`
    - 大きさ: 幅36×高さ48、`flex-shrink: 0`
    - 見た目: 角丸、`background: var(--surface-alt)`、`border: 1px solid var(--border)`
  - `.history-item-thumb img`: `width: 100%; height: 100%; object-fit: contain`
  - 人形のアイコン: `var(--muted)` で薄く描く。
  - `.history-item` の中で、名前の左に並べる。4つのテーマで確かめる。

#### 確かめたこと（ローカルの API と内蔵ブラウザ）
- **API**: `npx vitest run` で 98 件、すべて通過（88 → 98）。
- **互換（S8）**: 今の `main` のフロントで、次が今までどおり動いた。
  - 保存と立ち絵のアップロード
  - キャラシでの表示（2回目は 304）
  - 一覧の取得
- **サムネイルの作成（S12）**: 縦長・横長・透過・小さい画像・7.5MB のノイズ画像から、長い辺 128px の WebP ができた。
  - どれも 4KB 以下だった。
  - 小さい画像は拡大しない。
  - 透過は保たれる（隅の不透明度 0）。
- **保存の送信（S13）**: 6つの場合で、要件どおりに送った。

  | 場合 | 送ったもの |
  |---|---|
  | 画像を選んで新規保存 | 本文・元の画像・サムネイル |
  | 変更なしで上書き保存 | `PUT` だけ |
  | 画像を選び直して上書き保存 | 本文・元の画像・サムネイル |
  | 読み込み直して上書き保存 | `PUT` だけ |
  | JSON から新規保存 | 元の画像を取得して、新しいキャラへ写す（元の画像・サムネイル） |
  | 画像なしの新規保存 | 画像なし |

- **一覧（S14）**
  - サムネイルのある行は画像、無い行は人形のアイコンになる。
  - 画像は、パネルが見えたときに1回ずつ読み込む（`loading="lazy"`）。
  - 検索で7回描き直しても、パネルを開き直しても、サーバーへのサムネイルの取得は最初の2回だけだった（キャッシュ）。
- **自動作成（S15）**
  - 古いやり方で上げた画像と、今あるキャラの画像に、サムネイルができて表示された。
  - 壊れた画像のキャラは、警告を出して飛ばし、次へ進んだ。
- **マギロギ（S16）**
  - 自動作成（横長の画像）、画像を選んだ保存（両方を送る）、上書き保存（`PUT` だけ）が、シノビガミと同じだった。
  - 一覧から削除すると、サムネイルと元の画像の両方が 404 になった（S17）。
- **古いフロントで画像を差し替えた場合**
  - サムネイルが消えることは、API のテストで確かめた。
  - 作り直されることは、自動作成（古いやり方で上げた画像）で確かめた。
- **見た目**: 内蔵ブラウザが非表示の間はスクリーンショットが撮れなかった。4つのテーマでの見た目は、CSS 変数（`--surface-alt` / `--border` / `--muted`）を使っていることで担保し、公開後にユーザーが確かめる。
